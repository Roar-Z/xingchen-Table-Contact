汇表设计文档

这份文档记录页面为什么这么分、每一步为什么这样设计，主要给团队自己看，答辩时也能拿来解释取舍。 功能和字段细节在需求分析、接口文档里，这里不重复。

背景与目标

行政 HR 每个月要处理两类表格：一类是把请假明细并到年假余额上，算清楚谁扣年假、谁转事假； 另一类是把各车间的加班记录按部门和月份筛出来，回填到 HR 系统。这些表来自 OA、ERP、考勤机， 表头叫法都不一样，平时靠人手复制粘贴、写 VLOOKUP、对着模板一列列挪。

我们想做的不是“再做一个网页版 Excel”，而是把这段固定的手工活压成一次操作：

  • 源表不用先整理，导出什么样就传什么样，格式问题交给程序判断；
  • 导出哪些列不写死，以企业手上的 HR 导入模板为准；
  • 算完直接产出能导入的文件，有问题的行单独列出来，不用回头翻原表。
边界：系统不替代 HR 系统，也不改源数据。它只负责“读表、对齐字段、按规则算、出表、记录异常”， 原始文件和产出文件都留在本机。

谁在用

主要是行政和 HR 专员，他们熟悉 Excel，但不写代码，也不想学一套新系统。 所以页面里不用“ETL”“Schema”这类词，能说“表头”“列”“异常行”就说中文。

角色关心什么对设计的影响
HR 专员 处理了多少行，哪些行没成功，能不能直接导入 结果页先给统计和异常表，下载放在最后一步
部门助理 上传的表有没有识别错列 上传后马上把识别到的表头铺出来，能看能改
评审老师 系统边界清不清楚，数字是不是真算出来的 保留接口文档和样例数据，每一步都能追到数字来源

页面结构

整个系统只有两个入口：新建任务和任务记录。没有工作台，也没有仪表盘， 做完一次任务就离开或去看记录，不需要在首页停留。

新建任务页按业务顺序拆成五个步骤，用步骤条串起来，一次只展开一块。 因为我们自己试的时候发现，五个区块从上到下堆在一页，很难判断“现在做到哪”，出错也不知道该往上翻到哪； 拆成步骤后每一步只回答一个问题，底部固定“上一步 / 下一步”，条件没满足时按钮直接禁用并写明缺什么。

五个步骤

01上传文件 → 02字段映射 → 03业务规则 → 04执行与预览 → 05下载输出

1. 上传文件

源表可以选多个，目标模板只收一个。传完把每张表的行数、列数、表头标签直接显示出来， 用户一眼能看出“这一列其实是请假类型，不是部门”。模板区固定一句提醒：目标模板决定导出文件的表头和格式，格式不对 HR 系统会导入失败。

源表和模板缺任意一个，“下一步”就不亮，并在底部写清缺的是哪一项，避免配到一半跑到最后才报错。

2. 字段映射

左边是源表字段，右边是模板字段，中间按表头词典先给一版推荐。用户可以改来源列、删掉不用的行、 补上模板里多出来的列，也可以把当前这套对应关系存成“映射方案”，下次同类任务直接套用。

映射是否有效是实时判断的：文件被移除、源列不存在，这一行立刻回到“待映射”。 打开严格格式校验后，还有必填字段没映射就不让执行。

3. 业务规则

规则用一句中文写清楚就行，比如“先扣年假，不够的转事假”。页面另外给了两个内置模板 ——年假抵扣·不足转事假、按部门时间段筛选加班——点一下就填进去，现场演示不用手打。 写完后端会解析成场景、关联键、部门、日期区间和计算方式，解析结果放在映射区顶部，方便确认系统理解的和你说的是一回事。

4. 执行与预览

点“开始智能处理”后创建任务，页面每 1.2 秒拉一次进度，日志逐条往上走。 完成后先给统计（源表行数、命中条件、输出行数、年假抵扣、事假合计、异常行）， 再给两个预览表：处理成功的结果表、被隔离的异常数据。 预览只看前若干行，完整数据在文件里，避免页面被大表拖慢。

5. 下载输出

结果表按模板生成，文件名带日期；异常日志导出成 CSV，带 BOM，Windows 上的 Excel 双击不乱码。 这两个文件就是一次任务的交付物，下载完这一步就结束了。

模板决定导出列，不做格式比对

最早的做法是“上传模板后和内置格式比对，提示列不一致”，但这对用户没什么帮助： 企业 HR 系统要哪些列，我们照做就行。现在改成完全按模板走：

  • 解析阶段就把模板表头读进来，作为目标列返回（built_in=false）；
  • 导出时按模板列名逐列取值，顺序和模板一致，不多列也不少列；
  • 模板里某一列在源表找不到来源时，在映射区提示，不重排整份文件；
  • 没有模板就不推荐映射，也不允许运行。
样例数据也一样：点“载入样例”会同时载入配套的 HR 导入模板， 导出的列和真实模板一致，不存在“演示用内置格式、正式用模板”的差别。

规则和两个开关

业务规则是自然语言输入加内置快捷模板。后端先用规则和表头词典判断场景，把握够就不调用模型； 设置 HUBIAO_LLM_ENABLED 之后，只有规则拿不准时才会问一次模型，模型只返回场景和一句提示，不参与计算。

页面上有两个开关，都在后端真实生效：

开关默认行为
脏数据隔离 开启 问题行整行隔离，不进结果表，写进异常日志；关掉后照常输出，只在提示里说明有多少条问题数据。
严格格式校验 关闭 开启后模板列找不到来源、必填字段缺失、格式不对，直接判失败并说明原因，不再自动兜底。

异常怎么处理

异常没有合并成一句“出错了”，而是按原因分开，方便回原表核对：

类型触发条件
年假缺失请假单里的工号在年假余额表里找不到
时长异常请假或加班时长超出阈值，或者不是有效数字
日期异常起止日期解析失败，或者结束时间早于开始
工号缺失关键关联字段为空
字段缺失模板要求的必填列在源表里找不到
编码异常单元格出现 锟斤拷、烫烫烫、� 这类认不出的字符

编码异常是这一版补的：实际导出的表里经常混着 GBK 和 UTF-8 转换失败的乱码， 这种行就算字段齐了也不可信，放进结果表只会增加核对成本。

视觉与文案

整体是浅灰底、白卡片、一个主色，圆角 6px，不用渐变和大阴影，也不放插画和引导气泡， 避免把内部工具做成宣传页。

用途色值
主色#2B5FD9
页面背景#F5F6F8
正文#1F2329
次要文字#86909C
提醒#A96400

文案上有两条约束：

  • 按钮只说动作，例如“开始智能处理”“下载结果表”，不写“一键搞定”“立即体验”；
  • 报错要说清下一步做什么，例如“还缺目标模板，导出列由它决定”，而不是只给一个错误码。

技术方案

部分选型原因
前端Vue 3 + Vue Router + Element Plus表格和上传组件现成，时间花在流程上
后端Spring Boot 3.4.5（Java 21）文件处理和异步任务直接，部署只要一个 jar
表格读写Apache POI要同时读写 .xls 和 .xlsx，还得按模板写出能导入的文件
语义识别LangChain4j（可选）只在规则拿不准时兜底，关掉之后系统照样能跑
存储JSON 文件单机演示不用装数据库，任务和文件登记都放在 data/ 下

模型和计算是分开的：场景判断可以不确定，数字必须可复现。 同样的输入重复跑，统计结果一致，现场复验也方便。

和比赛流程的对应

上传源文件 → 上传目标模板 → 规则配置 → 执行智能处理 → 预览结果 → 异常处理 → 下载交付物

七个动作在界面上落在五个步骤里：上传源文件和上传模板合成第 1 步，预览、异常和下载分别是第 4、5 步。 合并的原因很简单，它们用的是同一批上传结果，拆开只会多一次点击。
