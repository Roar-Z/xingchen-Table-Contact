3. 运行方式

3.1 环境要求

  • JDK 21（java -version 能看到 21）
  • Maven 3.9+（如果直接运行 jar 则不需要）
  • Node.js 18+ 与 npm（只改前端时需要）

3.2 启动后端

方式一：直接运行已打包 jar

cd backend
java -jar target/huibiao-backend-0.8.2.jar

方式二：重新构建

cd backend
mvn -DskipTests package
java -jar target/huibiao-backend-0.8.2.jar

方式三：开发模式

cd backend
mvn spring-boot:run

启动后监听 http://127.0.0.1:8000。如果 ../frontend/dist 存在，后端会直接托管前端静态文件，访问根路径即可打开页面。

3.3 启动前端开发服务器

cd frontend
npm install
npm run dev

Vite 默认端口 5173，/api 代理到 127.0.0.1:8000。比赛演示建议用后端托管模式，只开一个端口，少一个失败点。

3.4 构建前端

cd frontend
npm run build

产物在 frontend/dist。构建完成后刷新后端根路径即可看到新页面。

4. 后端架构

4.1 请求链路

HTTP 请求
  → Controller（参数绑定）
  → Service（业务）
  → ExcelService / TaskStore / SettingsService / FileService
  → 本地文件
  → Jackson（snake_case）
  → HTTP 响应

任务创建是异步的：

POST /api/tasks
  → TaskService.create()
      → 生成任务编号、落 tasks.json、状态 queued
      → TaskRunner.run()（@Async，线程池 taskExecutor）
  → 立即返回任务快照

TaskRunner.run()
  → 读源文件、解析意图
  → SceneRouter 选择 LeaveSettlementService 或 OvertimeService
  → ProcessResult
  → ExportService 写 .xls / .xlsx / 异常日志
  → 更新任务状态、进度、日志

前端每 1.2 秒调用 GET /api/tasks/{id}，直到状态不是 queued/running。

4.3 表头识别

ExcelService 不假设第一行就是表头。逻辑：

  1. 从上往下扫描前 15 行；
  2. 跳过整行为空的行；
  3. 统计每行非空单元格数量；
  4. 用 HeaderCatalog.scoreRow() 计算这一行与标准字段别名的匹配分数；
  5. 选择“非空数量 × 0.4 + 匹配分数 × 0.6”最高的一行；
  6. 如果最高分太低，退回“非空单元格最多”的行。

年假表第一行是标题，只有 1 个非空单元格，匹配分数低；第二行有 9 个表头，匹配分数高，所以识别为第 2 行。识别结果写入 FileMeta.headerRow（从 1 开始），后续读数据从下一行开始。

4.4 字段匹配

HeaderCatalog 里每个标准字段有一组别名，例如：

emp_no      工号、员工编号、人员编号、工号编码、员工号
name        姓名、申请人、员工姓名、人员姓名
department  部门、部门名称、所属部门、班组
leave_type  请假类型、假别、缺勤类别、假期类型
start_date  起始日期、开始日期、请假开始日期、日期
days        天、天数、请假天数
hours       小时、时长、请假小时
annual_left 剩余年假、年假余额、可用年假

匹配时先归一化：去空格、全角转半角、转小写、去掉常见后缀（如“（必填）”）。然后按顺序：

  1. 归一化后完全相等：1.0；
  2. 一方包含另一方：0.86；
  3. 编辑距离 / 最大长度 ≤ 0.3：0.6–0.85；
  4. 否则 0。

别名由 settings.json 合并，手工补充的别名会参与之后的任务。emp_no 的别名里特意不放“申请人”，因为 OA 表里“申请人”是姓名，放了会导致工号列匹配错。

4.5 日期解析

TextUtils.parseDate() 支持：

  • Excel 数值日期（POI 的 DateUtil.isCellDateFormatted 已经在读取时转成字符串，这里主要处理文本）；
  • 2026-04-01、2026/4/1、2026.4.1；
  • 4/1/26、4/1/2026；
  • 2026年4月1日；
  • 带时间的 2026-04-01 08:30。

解析失败返回 null，由调用方决定是跳过还是记异常。加班筛选里日期解析失败会记“日期异常”，请假结算里起止时间解析失败会记“时间异常”，但不影响时长按“天/小时”计算。

TextUtils.combineDateTime() 把“起始日期 + 起始时间”拼成 yyyy-MM-dd HH:mm。如果只有日期，起始补 00:00，结束补 23:59，这是 HR 系统能接受的保守值。

4.6 假期结算实现

入口：LeaveSettlementService.settle(List<FileRef>, IntentResult, TaskConfig)。

步骤：

  1. 从 files 里找角色为 leave_request 和 annual_balance 的文件；
  2. 读请假单表头，按映射/词典找列：工号、姓名、部门、请假类型、起始日期、起始时间、结束日期、结束时间、天、小时；
  3. 读年假表，找工号列和剩余年假列，建立 Map<工号, 天数>；
  4. 逐行处理请假单：
  5. 工号为空 → 异常“工号缺失”；
  6. 解析起止时间、计算总时长；
  7. 总时长 ≤ 0 → 异常“时长异常”；
  8. 查年假余额；找不到 → 异常“年假缺失”，按 0 处理；
  9. 计算可扣年假和事假；
  10. 有年假 → 输出年假行；有事假 → 输出事假行；
  11. 统计年假小时、事假小时、输出行数、异常行数；
  12. 返回 ProcessResult。

核心代码（简化）：

double totalHours = hoursOf(row, daysCol, hoursCol, preferred, start, end, workday);
Double leftDays = balances.get(empNo);
double deduct = canDeduct ? Math.min(totalHours, Math.max(0, leftDays) * workday) : 0;
if (deduct > 0) {
    result.addRow(outputRow(empNo, name, dept, "年假", start, end, deduct));
}
double remain = TextUtils.round1(totalHours - deduct);
if (remain > 0) {
    result.addRow(outputRow(empNo, name, dept, deduct > 0 ? "事假" : category, start, end, remain));
}

几个容易踩的坑：

  • 小时列为 0：OA 导出的“小时”列在按天请假时是 0，不能直接采用。hoursOf() 先看小时是否大于 0，否则用天 × 每日工时；
  • 映射到“天”列：用户如果在界面上把“合计小时”指到“天”，代码不能又乘一次 8。preferredHoursColumn() 会检查前 100 行小时列是否有效，只有无效时才建议天列；
  • 年假为 0 与缺失：余额为 0 是有记录，不记异常；余额表里没有工号才记“年假缺失”；
  • 拆分后行数变多：统计里单独给出“输出行数”和“源表行数”，并在警告里说明拆分原因。

4.7 加班筛选实现

入口：OvertimeService.process()。

  1. 找角色为 overtime 的文件；
  2. 找列：工号、姓名、部门、职位、起始日期、申请加班；
  3. 逐行：
  4. 部门配置了且不包含筛选值 → 跳过，计入 skipped_rows；
  5. 日期解析失败 → 异常；
  6. 日期不在区间 → 跳过；
  7. 申请加班空 → 异常“字段缺失”；
  8. 非数字或负数 → 异常“时长异常”；
  9. 正常 → 输出，累计小时；
  10. 输出日期格式 M/d/yy。

样例 ERP 表 36001 行，筛选总装车间 2026 年 4 月，命中 4597 行，合计 26859.5 小时。全部行都有有效加班时长，所以异常 0 条。

4.8 异常模型与统计

Anomaly：

public record Anomaly(int row, String source, String reason, String raw, String type) {}

ProcessResult 同时保存 rows（完整结果）和 preview（前 20 行），避免把几万行全传给前端。finish() 统一计算 outputRows 和 anomalyRows，防止各服务统计口径不一致。

异常占比：

ratio = anomaly_rows / total_rows * 100
if ratio > anomaly_threshold（默认 20）：
    任务状态 = warning
    警告里提示先看异常日志

这里只是提醒，不阻断文件生成。因为异常可能集中在少数部门，整批不生成会让业务人员无法继续。

4.9 任务持久化

TaskStore 用 data/tasks.json 保存任务数组。写入时先写 tasks.json.tmp，再 Files.move(..., REPLACE_EXISTING, ATOMIC_MOVE)，减少写到一半断电导致文件损坏。

任务编号：

T + yyyyMMdd + "-" + 四位序号
例如 T20261027-0001

序号按当天已有任务的最大值 +1，重启后从文件里读，不会重复。

任务执行时，TaskRunner 先从 TaskStore 重新取一次任务对象，避免和接口线程同时改同一个对象。每个阶段更新后立即 store.put(task)，前端轮询能看到进度。

4.10 文件路径安全

  • 上传文件保存名由系统生成：{fileId}.{ext}，不使用用户文件名；
  • 下载接口只接受任务 artifacts 里登记过的 name；
  • 解析出的路径 normalize() 后必须仍位于 data 根目录，否则拒绝；
  • 任务记录只增不删，避免误删已经交付给 HR 的结果。

这些措施不能替代真正的权限系统，但能避免最常见的路径穿越和误删。

5.1 页面与路由

5.2 API 封装

src/api.js 统一处理：

  • request()：拼接口前缀、解析 JSON、非 2xx 抛错并读 detail；
  • upload()：FormData，不手动设 Content-Type，让浏览器带 boundary；
  • 接口函数：health、tasks、task、upload、analyze、prepareDemo、preview、createTask、downloadUrl；
  • apiState 记录后端是否在线，侧边栏和列表页共用这个状态。

页面流程里用的是 analyze → createTask → task 轮询 → downloadUrl。preview 只做试算、不落任务记录，留给二次开发和命令行验证使用，页面上不再单独放试算按钮。

后端字段是 snake_case，前端直接用，不再转换。这样接口文档、网络面板、代码里的字段名一致，排查问题快。

5.3 离线处理

前端不再内置 Mock 数据。后端没启动时，上传、解析、执行都会失败，页面显示明确的启动提示，不返回假任务、假统计。这样答辩现场看到的结果一定来自真实处理。

5.4 轮询与清理

TaskDetail.vue 在 onMounted 时拉一次详情，处理中通过 setTimeout 每 1.2 秒再拉；状态进入 done、warning、failed 后停止；组件卸载或任务编号变化时调用 stopPolling() 清理定时器，避免旧任务的请求继续覆盖新页面。

NewTask.vue 点“开始智能处理”后创建任务，用同一套 1.2 秒轮询把进度和结果就地刷出来，完成后不跳页；离开页面时同样清定时器。

5.5 样式组织

styles/base.css 是全局设计系统文件，包含：

  • CSS 变量：颜色、圆角、字体；
  • 布局：shell、sidebar、main-area、topbar、page-head；
  • 组件：panel、dropzone、file-list、data-table、status、metrics、artifact、toast；
  • 响应式断点：960、720。

没有 CSS-in-JS，也没有 Tailwind。列表页、详情页用 base.css 里的通用类；NewTask.vue 的区块布局写成 scoped style，Element Plus 的主题变量也只在 .nt 这一层覆盖，不影响其它页面。

7.5 接口与页面

  • GET /api/health 返回 200；
  • GET /api/tasks 支持状态、关键词、分页，返回各状态数量；
  • 任务详情轮询从 queued → done；
  • 下载中文文件名，响应头 Content-Disposition: attachment; filename*=UTF-8''...；

7.6 已知未覆盖

  • 没有做 10 万行以上的压力测试；

  • 没有做 Office 2003 真机导入测试，只用 LibreOffice/POI 校验；
  • 没有做模型开启后的稳定性长跑，只验证了单次调用和失败回退。

8. 常见问题

8.1 启动报端口占用

Get-NetTCPConnection -LocalPort 8000 -State Listen
Stop-Process -Id <PID> -Force

或者改 application.yml 的 server.port。

8.2 上传后提示“表头识别失败”

先看文件第一行是不是合并单元格标题。系统会尝试前 15 行，如果标题行特别长或表头不在前 15 行，需要手工把表头移到前面。也可以直接在 settings.json 的别名字典里补充常见叫法，改完重启后端。

8.3 年假全部按事假输出

检查：

  1. 年假文件角色是否为“年假余额”；
  2. 年假表工号列是否被识别为“工号”；
  3. 工号格式是否一致（E10192 和 10192 不会自动补前缀）；
  4. 年假余额列是否被识别为“剩余年假”。

8.4 下载 404

产出文件可能被手工清理。任务详情里如果 artifacts 为空，用同样的源文件重新新建一次任务，不要手工往产出目录塞文件。

8.5 前端页面空白

确认 frontend/dist/index.html 存在；如果只启动了 Vite，访问 5173，不要访问 8000。后端托管模式需要先 npm run build。

8.6 中文乱码

  • 源码统一 UTF-8；
  • 启动脚本里执行 chcp 65001；
  • CSV 上传时如果乱码，确认文件是 UTF-8 或 GBK，系统会尝试回退。

9. 扩展新场景的步骤

以“供应商对账”为例：

  1. 在 HeaderCatalog 增加标准字段，例如 supplier_no、invoice_no、amount；
  2. 新建 SupplierReconciliationService，实现 process(List<FileRef>, IntentResult, TaskConfig)；
  3. 在 SceneRouter 增加分支；
  4. 在 SettingsService 增加输出模板；
  5. 在 IntentService 增加场景关键词和字段映射建议；
  6. 前端新建任务页增加场景文案和示例；
  7. 用真实样例做回归，补充异常类型。

不需要改任务框架、文件存储、异常日志、导出服务，这些是复用的。

11. 代码约定

  • 后端包名 com.xingchen.huibiao，类名用业务词，不用 Util2、Helper；
  • 对外 JSON 一律 snake_case，内部 Java 字段用 camelCase；
  • 异常信息面向用户，技术细节写日志；
  • 金额/工时用 double + 统一四舍五入到 1 位，暂不引入 BigDecimal（当前精度足够，后续做薪资要换）；
  • 前端不直接拼 HTML，用户输入通过 Vue 文本插值；
  • 新增接口必须同步更新 docs/05-接口文档.md 和 /docs/ 静态页；
  • 提交前至少跑一次后端打包和前端构建。

12. 交付说明

交付包包含源代码、样例数据、比赛文档、已构建前端和后端 jar。现场演示步骤：

  1. 双击 backend/start.cmd（或运行 jar）；
  2. 浏览器打开 http://127.0.0.1:8000；
  3. 任务记录页应已有两条示例任务（首次启动自动生成）；
  4. 点“新建任务”，按步骤条走一遍：上传源表与模板 → 确认映射 → 填写规则 → 开始处理与预览 → 下载；
  5. 下载 HR 导入表，打开异常日志；
  6. 打开 /docs/ 展示接口文档。

如果现场不希望自动生成示例任务，把 application.yml 里的 app.seed-demo 改为 false，并清空 backend/data 后重启。
